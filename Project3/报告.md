# 基于 Claude Code 的 tinyRocket 全流程自动化 Agent 开发 — 项目报告

**小组成员：** 杜昊、曹闰程
**课程作业：** EDA 系统 AgentForRISCV Project3
**工艺节点：** SkyWater 130nm (sky130hd)
**设计目标：** tinyRocket RISC-V 处理器完整前后端自动化实现（RV64GC，64-bit）

---

## 一、项目概述

本项目构建了一套基于 AI Agent 的 RISC-V 芯片 EDA 自动化系统，实现从 RTL 生成到版图完成的全流程自动化。系统以 Claude Code 为 Agent 核心，通过 MCP 封装 Docker 容器操作，结合 Skill 编排完成完整的前后端流程，并具备自动诊断、策略性修复和 PPA 优化迭代能力。

## 二、基础要求完成情况

### 2.1 Docker + ChipYard 环境

项目使用两个 Docker 容器构成完整工具链：

| 容器名 | 镜像 | 用途 |
|--------|------|------|
| `chipyard-agent` | `ictmrc/chipyard-image:1.9.1-ubuntu-22.04` | RTL 生成（Chisel/FIRRTL） |
| `orfs-agent` | `openroad/orfs:latest` | 综合、布局、布线（OpenROAD） |

两个容器均通过 `-v ./persist:/workspace/persist` 挂载宿主机持久化目录，实现数据共享与结果保存。

ChipYard 工具链通过容器内 conda 环境提供，激活方式：
```bash
source /workspace/chipyard/.conda-env/etc/profile.d/conda.sh
conda activate /workspace/chipyard/.conda-env
```
激活后自动配置 `RISCV`、verilator、java、sbt 等工具路径。

### 2.2 ChipYard 生成 tinyRocket Verilog RTL

通过 `chipyard-automation` MCP 的 `generate_rtl` 工具，在容器内运行：
```
make verilog CONFIG=TinyRocketConfig
```

生成产物保存在 `persist/rtl_output/chipyard.TestHarness.TinyRocketConfig/`，包含：
- 顶层 SystemVerilog 文件（`RocketTile` 模块）
- SRAM 黑盒需求文件（`*.mems.conf`）
- 注解文件（`*.anno.json`）

`generate_rtl` 完成后自动执行 firtool 后处理，以 `noAlwaysComb,disallowLocalVariables` 等 lowering options 将 `.fir` 重新编译为可综合纯 Verilog，删除含 packed array 的验证/外设模块，生成 `verilog_synth/filelist.f`。ORFS 综合直接使用 ChipYard 生成的 RTL。

### 2.3 MCP Server 封装

项目实现了两个 MCP Server，注册在 `.mcp.json`，共封装 **12 个工具**：

#### `chipyard-automation`（`mcp_server/src/chipyard.js`）

| 工具 | 功能 |
|------|------|
| `start_chipyard` | 启动容器，挂载 persist，支持自定义镜像 |
| `generate_rtl` | 激活 conda，运行 make verilog，firtool 后处理生成 `verilog_synth/`，30 分钟超时 |
| `read_mems_conf` | 解析 `*.mems.conf`，返回结构化 SRAM 黑盒列表 |
| `list_rtl_files` | 列出 RTL 输出目录内容 |
| `read_rtl_file` | 读取 RTL 文件，路径限制在 `rtl_output/` 内 |
| `stop_chipyard` | 停止并删除容器 |

#### `orfs-agent`（`mcp_server/src/index.js`）

| 工具 | 功能 |
|------|------|
| `run_stage` | 执行 ORFS 阶段（synth/floorplan/place/cts/route/finish），1 小时超时 |
| `get_metrics` | 读取 `metadata.json`，返回完整 PPA 指标 |
| `read_container_file` | 读取容器内日志/报告 |
| `list_files_container` | 浏览容器内目录 |
| `read_file` | 读取宿主机设计文件，路径限制在项目目录内 |
| `write_file` | 写入宿主机设计文件，路径限制在项目目录内 |

**安全设计：** `read_file`/`write_file` 均实现路径边界检查，防止目录穿越；`run_stage` 自动附加 `SKIP_CTS_REPAIR_TIMING=1` 规避 WSL2 已知崩溃问题。

### 2.4 Skill 编排完整后端流程

项目在 `.claude/skills/` 下实现了 5 个 Skill：

| Skill | 触发命令 | 功能 |
|-------|---------|------|
| `flow.md` | `/flow` | 完整前后端流程编排（RTL生成→SRAM映射→PnR→报告） |
| `summary.md` | `/summary` | PPA 分析与报告生成 |
| `debug.md` | `/debug` | 环境问题诊断与修复 |
| `report.md` | `/report` | 版图完成后生成编号报告，引导优化迭代 |
| `optimal.md` | `/optimal` | 后端 Bug 修复与 PPA 参数调优指南 |

`/flow` Skill 编排的完整后端流程：

```
start_chipyard()
  → generate_rtl(config)
  → read_mems_conf(config)          # 分析 SRAM 需求
  → [SRAM 工艺映射，更新 sram_macros.v]
  → run_stage("synth")
  → run_stage("floorplan")
  → run_stage("place")
  → run_stage("cts")
  → run_stage("route")
  → run_stage("finish")
  → get_metrics()                   # 输出 PPA 报告
```

## 三、进阶要求完成情况

### 3.1 自动诊断错误类型与针对性修复

`/debug` 和 `/optimal` Skill 实现了分类诊断与针对性修复策略，覆盖以下错误类型：

#### 时序违例（WNS < 0）
- **诊断方式：** `get_metrics()` 读取 `finish__timing__setup__ws`，`read_container_file` 读取关键路径报告
- **修复策略：** 根据违例严重程度分级处理——轻微违例降低 `PLACE_DENSITY`，严重违例调整 `constraint.sdc` 时钟周期
- **非盲目重试：** 每次修复前先定位关键路径，确认是布线绕线延迟还是逻辑深度问题，再选择对应策略

#### 拥塞/DRC 错误
- **诊断方式：** 读取 `3_1_place.log` 中的 `overflow` 值，`5_2_route.log` 中的 `violation` 数量
- **修复策略：** overflow > 0.2 时优先降低 `PLACE_DENSITY`；DRC > 0 时检查拥塞热点层，调整 `CORE_UTILIZATION` 和 `CORE_ASPECT_RATIO`

#### 综合失败
- **诊断方式：** 读取 `1_1_yosys.log`，区分"模块找不到"、"SV 语法不支持"、"SRAM 黑盒未识别"三类
- **修复策略：** 各类错误有独立修复路径，不混用

#### WSL2 环境崩溃
- **自动规避：** `run_stage` 工具已内置 `SKIP_CTS_REPAIR_TIMING=1`，无需人工干预

### 3.2 策略性 PPA 优化与迭代记录

`/report` 和 `/optimal` Skill 共同实现了有记录的优化迭代系统：

#### 优化迭代机制

```
/report 生成 report_1.md（初始基准）
  → 询问用户优化目标
  → 用户指定优化方向
  → 记录 log_1.md（变更内容、优化依据、预期效果）
  → 修改 config.mk / constraint.sdc
  → 重跑后端流程
  → 生成 report_2.md（优化后结果）
  → 对比 report_1 与 report_2，评估优化效果
  → 继续迭代或结束
```

#### 序号对应关系

| 文件 | 内容 |
|------|------|
| `result/report_1.md` | 初始实现 PPA 报告 |
| `result/log_1.md` | 第一次优化：变更参数、原因、预期 |
| `result/report_2.md` | 第一次优化后 PPA 报告 |
| `result/log_N.md` | 第 N 次优化记录 |
| `result/report_{N+1}.md` | 第 N 次优化后报告 |

#### 优化策略体系（`/optimal` Skill）

| 优化目标 | 关键参数 | 调整方向 | 副作用 |
|---------|---------|---------|--------|
| 提高 Fmax | `constraint.sdc` 时钟周期 | 减小 | 可能引入时序违例 |
| 修复时序违例 | 时钟周期 / `PLACE_DENSITY` | 增大 / 减小 | 性能下降 / 面积增大 |
| 缩小面积 | `CORE_UTILIZATION` | 增大 | 拥塞风险上升 |
| 缓解拥塞 | `PLACE_DENSITY` | 减小 | 面积增大 |
| 改变芯片形状 | `CORE_ASPECT_RATIO` | 调整 | 影响宏摆放 |

## 五、关键技术点

1. **RTL 可综合化（SV→V 转换）**：ChipYard 生成的 SystemVerilog 经 firtool 后处理转换为纯 Verilog，消除 `always_ff`/`always_comb`/packed array 等 Yosys 不支持的语法。同时通过 `--repl-seq-mem` 提取 SRAM 黑盒，过滤验证/外设模块后生成 `verilog_synth/filelist.f`，ORFS 直接综合 ChipYard 生成的 RTL。

2. **SRAM 工艺映射**：firtool 提取的 SRAM 黑盒（`*_combMem`）通过 `sram_macros.v` 映射到 sram22_sky130 物理宏。64-bit TinyRocketConfig 的 ICache data array（深度 4096×32）超出单个宏容量，采用 bank 分割方案：以 `addr[11]` 为片选，将两个 `sram22_2048x32m8w8` 组成伪双 bank，并用寄存器 `bank_sel_r` 对齐输出 mux 时序。

3. **模块缺失处理策略**：firtool 删除的模块在上层仍有实例化引用。有输出端口的模块必须使用可综合 stub（所有输出赋 0），不能用 `(* blackbox *)`，否则 Yosys 保留该模块导致 OpenROAD 找不到对应 LEF。无输出端口的模块（TLMonitor 系列）可用 blackbox stub，同时去掉 Yosys `hierarchy -check` 严格模式。

4. **GDS 合并**：sram22_sky130 宏的 GDS 文件以 `.gds.gz` 压缩存储，需在容器内 `gunzip -k` 解压后通过 `ADDITIONAL_GDS` 变量（非 `GDS_FILES`）传入 ORFS finish 阶段合并。

5. **WSL2 兼容性**：CTS 后 `detailed_placement` 在 WSL2 下因指令集不兼容崩溃，通过在 MCP server 中自动附加 `SKIP_CTS_REPAIR_TIMING=1` 透明解决，用户无感知。

6. **路径安全**：MCP server 的文件读写工具均实现 `PROJECT_ROOT` 边界检查，防止 Agent 误操作系统文件。

7. **超时管理**：`generate_rtl` 设置 30 分钟超时，`run_stage` 设置 1 小时超时，覆盖最长的布线阶段（本次布线实际耗时约 13 分钟）。

8. **可扩展性**：所有设计名通过参数传入（`config`、`design_nickname`），不硬编码，支持从 TinyRocketConfig 扩展到 MediumBoomConfig 等其他 ChipYard 配置。
